# 网络八股荟萃

## 2. 计算机网络五层模型分别负责什么？
- **应用层**：负责应用进程之间的交互，如 HTTP、DNS、FTP 等。
- **传输层**：负责向两个主机中进程之间的通信提供数据传输服务，如 TCP 和 UDP。
- **网络层**：负责为分组交换网上的不同主机提供通信服务，选择合适的路由，如 IP 协议。
- **数据链路层**：负责在相邻节点之间的链路上无差错地传输以帧为单位的数据。
- **物理层**：负责在物理媒体上实现比特流的透明传输。

## 3. IP 地址和 Mac 地址有啥区别？
- **层级不同**：IP 地址处于网络层，MAC 地址处于数据链路层。
- **分配方式不同**：IP 地址基于网络拓扑结构分配（可变），MAC 地址由制造商烧录在网卡上（全球唯一，通常不可变）。
- **作用不同**：IP 地址用于标识网络中的逻辑位置（解决数据如何在整个网络中路由），MAC 地址用于局网内的设备物理寻址（解决数据在同一局域网中如何发送给目标主机）。

## 4. 说一说三次握手
1. **第一次握手**：客户端发送 SYN 报文并进入 SYN_SENT 状态，指明客户端打算连接的服务器端口和初始序号 ISN。
2. **第二次握手**：服务器收到 SYN 后，返回 SYN+ACK 报文确认客户端的 SYN，同时自己也发送一个 SYN 报文，进入 SYN_RCVD 状态。
3. **第三次握手**：客户端收到服务器的 SYN+ACK 后，发送 ACK 报文确认。服务器收到 ACK 后，双方进入 ESTABLISHED（已连接）状态。

## 5. 三次握手过程中可以携带数据吗
- **第一次和第二次**（SYN 报文段）不可以携带数据，如果允许携带数据，服务器极易受到 SYN 泛洪攻击，会导致服务器消耗大量内存。
- **第三次握手**是可以携带数据的，因为此时客户端已经知道服务器已经准备好了（进入了 ESTABLISHED 状态），它可以先把数据附在 ACK 中发送给服务器。

## 6. 说一说四次挥手
1. **第一次挥手**：客户端发送 FIN 报文给服务端，表示自己没有数据要发送了，进入 FIN_WAIT_1 状态。
2. **第二次挥手**：服务端收到 FIN，发送 ACK 报文，进入 CLOSE_WAIT 状态。此时处于半关闭状态，客户端不能发数据，但服务端如果还有数据可继续发。
3. **第三次挥手**：服务端数据发送完毕，向客户端发送 FIN 报文，进入 LAST_ACK 状态。
4. **第四次挥手**：客户端收到 FIN，发送 ACK 报文，进入 TIME_WAIT 状态。服务端收到后进入 CLOSED 状态；客户端等待 2MSL 后也进入 CLOSED 状态。

## 7. 为什么 TIME-WAIT 状态必须等待 2MSL 的时间呢？
1. **保证最后一个 ACK 报文能够到达服务端**：如果 ACK 丢失，服务端会重传 FIN 报文，2MSL 足够客户端收到重传的 FIN 并在此发送 ACK。
2. **防止“已失效的连接请求报文段”出现在本连接中**：经过 2MSL 能够使本连接持续的时间内所产生的所有报文段都从网络中消失，保证在下一个新的连接中不会出现旧的报文段请求。

## 8. 说一说TCP与UDP的区别
- **面向连接**：TCP 是面向连接的，UDP 是无连接的。
- **可靠性**：TCP 提供可靠传输（确认、重传、排序等），UDP 尽最大努力交付，不保证可靠。
- **传输形式**：TCP 面向字节流，UDP 面向报文。
- **开销**：TCP 首部较大（20-60字节），UDP 首部小（8字节），开销小。
- **适用场景**：TCP 适用于要求可靠传输的场景（文件传输、邮件），UDP 适用于实时应用（音视频、游戏）。

## 9. TCP 和 UDP 分别对应的常见应用层协议有哪些？
- **TCP**：HTTP、HTTPS、FTP、SMTP、POP3、SSH、Telnet。
- **UDP**：DNS（也可TCP）、DHCP、TFTP、SNMP、视频流媒体。

## 10. 浏览器对同一 Host 建立 TCP 连接到的数量有没有限制？
有限制，通常现代浏览器（如 Chrome, Firefox, Edge）对同一个域名（Host）的最大并发连接数限制在 6 个左右。

## 11. 说一说HTTP1.0，1.1，2.0 的区别
- **HTTP/1.0**：短连接（每次请求新建连接），头部不压缩，存在队头阻塞问题。
- **HTTP/1.1**：默认开启长连接（keep-alive），支持管道化，增加了缓存控制字段和 Host 字段。
- **HTTP/2.0**：采用二进制格式而非文本；多路复用（同域名只需一个TCP连接）；头部压缩（HPACK算法）；支持服务端推送。

## 12. 什么是SQL 注入？举个例子？
**SQL注入**是指攻击者将恶意SQL代码插入到应用的输入参数中，从而欺骗数据库执行非授权操作。
**例子**：处理登录的语句 `SELECT * FROM users WHERE username = '$name' AND password = '$pwd'`。如果用户输入名字为 `' OR '1'='1`，则语句变成 `... WHERE username = '' OR '1'='1' ...`，直接绕过密码验证登录成功。

## 13. 谈一谈 XSS 攻击，举个例子？
**XSS（跨站脚本攻击）**是指攻击者向网页注入恶意的客户端脚本（通常是 JavaScript），当用户浏览该网页时脚本会在其浏览器中执行。
**例子**：用户在评论区输入 `<script>alert(document.cookie)</script>` 并提交。如果网站没做转义，其他用户查看该评论时，浏览器就会弹出显示其 cookie 信息的弹窗，或者将其窃取发送到攻击者服务器。

## 14. 什么是DDos攻击？
**DDoS（分布式拒绝服务攻击）**，攻击者控制大量位于不同位置的已被入侵的计算机（僵尸网络）齐向目标服务器发送大量海量请求或数据包，耗尽目标的网络带宽或系统资源，导致正常用户无法访问目标服务。

## 15. GET请求中URL编码的意义
URL 中只能包含合法字符（ASCII 的一个子集）。如果不进行编码，对于特殊字符（如中文字符、空格、甚至是某些标点及协议控制字符 `&`, `=`, `?`），浏览器或服务器在解析 URL 时会产生歧义甚至报错。编码是为了保证 URL 的合法性与数据传输的一致性。

## 16. HTTP 哪些常用的状态码及使用场景？
- **200 OK**：请求成功（常见场景）。
- **301 Moved Permanently**：永久重定向（网站更换新域名）。
- **302 Found**：临时重定向。
- **304 Not Modified**：资源未修改，客户端可使用缓存。
- **400 Bad Request**：客户端请求语法错误。
- **401 Unauthorized**：未授权，要求身份验证。
- **403 Forbidden**：服务器拒绝执行（权限不足）。
- **404 Not Found**：请求资源不存在。
- **500 Internal Server Error**：服务器内部故障。
- **502 Bad Gateway**：网关或代理出错。

## 17. HTTP状态码301和302的区别，都有哪些用途？
- **301 永久重定向**：表示旧 URL 已被永久废弃，搜索引擎抓取时应更新URL。用于域名整体迁移、http向https全站重定向。
- **302 临时重定向**：目标资源暂时存放在不同地址。用于未登录用户访问受限页面转跳到登录页、促销活动临时跳转等。

## 18. 简单说下每一层对应的网络协议有哪些？
- **应用层**：HTTP, DNS, FTP, SMTP
- **传输层**：TCP, UDP
- **网络层**：IP, ICMP, ARP, OSPF
- **数据链路层**：PPP, CSMA/CD, 以太网协议

## 19. ARP 协议的工作原理？
ARP 用于将目标的 IP 地址解析为 MAC 地址。
工作原理：主机先查询自己的 ARP 缓存表，若有目标 IP 和 MAC 映射则直接使用。若没有，主机在局域网内发起 ARP 广播请求（"谁是这个 IP 的目标，请告诉我你的 MAC 地址"）；目标主机收到广播后，发现 IP 相符，便以单播形式返回 ARP 响应（包含自己的 MAC 地址）。主机收到响应后更新缓存表，进行数据链路层封装。

## 20. 保活计时器的作用？
当客户端和服务端建立 TCP 连接后，如果客户端突然宕机没有向服务端发送任何数据。为了防止服务端一直等下去浪费资源，保活计时器会起作用：服务端每收到一次客户端数据就重置计时器；若设定的时间（如2小时）内无数据，则服务端发探测报文，连续数次探测无响应则关闭连接。

## 21. TCP 协议是如何保证可靠传输的？
TCP 依靠以下机制保证可靠：
1. **序列号与确认应答**：将报文分段并编号，接收方通过 ACK 确认已收到的包。
2. **校验和**：检验数据在传输过程中有无损坏。
3. **超时重传**：发送数据后启动定时器，若超时未收到确认则重传。
4. **流量控制**：利用滑动窗口机制协调发送接收速率，防止缓存溢出。
5. **拥塞控制**：慢开始、拥塞避免、快重传、快恢复，避免整个网络拥塞。

## 22. 谈谈你对 ARQ 协议的理解？
ARQ（自动重传请求协议）是指一种在不可靠链路上实现可靠传输的机制。主要包含**停止等待 ARQ** 和 **连续 ARQ（包括 Go-Back-N 和 选择重传）**。当发送方没有在规定时间内收到接收方的确认（ACK），它会自动重新发送数据。它是 TCP 可靠传输核心机制的基础。

## 23. 什么是流量控制？
流量控制是为了防止发送方发送数据过快，导致接收方缓冲区满而丢失数据的问题。它是点对点的控制，调节发送方的发送速率匹配接收方的处理能力。

## 24. TCP 是如何实现流量控制的？
通过**滑动窗口机制**来实现。通信双方在 TCP 报文头中携带窗口大小字段（Window Size），通过首部窗口大小值反馈给发送方接收端当前的接收缓冲区剩余空间，发送端根据这个窗口大小动态调整发送窗口，从而控制数据发送速率。

## 25. 什么是滑动窗口
滑动窗口是 TCP 协议中实现流量控制和提供可靠传输的一种技术。发送方和接收方各自维护一个“窗口”，窗口是指允许发送 / 接收并且不需要等待确认应答的数据范围。随着数据的发送和确认应答的接收，窗口沿着字节流向前“滑动”。

## 26. 那你讲一讲什么是TCP粘包和拆包？
- **粘包**：两个或多个数据包在接收端被合并成一个包，导致边界模糊。
- **拆包**：一个完整的数据包被拆分成多个小包发送到接收端，接收端只收到部分数据。
- **原因**：TCP 是基于字节流的面向连接的协议，没有消息边界。
- **解决**：在应用层设定边界，如定长报文、包头加长度字段、或者使用特殊分隔符（如 HTTP 的 \r\n）。

## 27. forward 和 redirect 的区别？
这里常指 Web 开发中：
- **Forward（转发）**：服务器内部操作，客户端浏览器地址栏 URL 不会改变；只能在同一个应用内跳转；效率高（共享 Request 对象）。
- **Redirect（重定向）**：服务器告知浏览器换一个地址访问，本质上发起了两次 HTTP 请求；URL 会发生改变；可以重定向到任意网址。

## 28. HTTP 常见方法有哪些？
GET，POST，PUT，DELETE，HEAD，OPTIONS，PATCH，TRACE。

## 29. 说一说POST与GET有哪些区别
- **语义约束**：GET 获取资源；POST 提交数据、新增或修改资源。
- **参数传递**：GET 参数附在 URL 后面；POST 参数放在请求体（Body）中。
- **缓存与历史**：GET 请求可被浏览器缓存、保留历史记录；POST 不会。
- **安全性与长度限制**：GET 放在 URL 易暴露且受 URL 长度限制；POST 在请求体中相对更安全，无理论长度限制。

## 30. 在浏览器中输入 URL 地址到显示主页的过程？
1. **URL 解析与 DNS 解析**：查缓存，解析 IP。
2. **TCP 三次握手**：客户端与服务器建立连接。
3. **发起 HTTP/HTTPS 请求**：根据连接发送网络层报文。
4. **服务器响应**：处理请求并返回包含 HTML 代码的 HTTP 报文。
5. **浏览器渲染阶段**：解析 HTML、应用 CSS、执行 JavaScript 并最终绘制网页页面给用户。
6. **TCP 四次挥手**：连接释放（或保持长连接）。

## 31. DNS 的解析过程？
1. 查看浏览器缓存 -> 操作系统缓存（DNS Client 服务/hosts文件）-> 路由器缓存。
2. 若本地无缓存，向本地域名服务器查询。
3. 本地域名服务器依次向：根域名服务器 -> 顶级域名服务器 -> 权威域名服务器（递归或迭代方式查询）。
4. 本地域名服务器最终获取到 IP 并返回给本地主机，并缓存起来。

## 32. 为了 DNS 解析更多，你觉得可以用到哪些优化手段？
1. DNS 预解析（DNS Prefetching），在 html 头通过 `<link rel="dns-prefetch" href="...">`。
2. 使用更近/更快的公共 DNS 节点。
3. 把静态资源放在不同域名下（增加并发，但会增加DNS解析，权衡取舍）；或者是 CDN 边缘节点缓存。

## 33. 什么是 HTTP 长连接？
在 HTTP/1.1 中默认开启（Connection: keep-alive）。即在完成一个 HTTP 请求/响应之后，底层的 TCP 连接不断开，而是保持畅通，如果后续有相同主机发来请求，直接复用该 TCP 连接，避免了建立连接的开销。

## 34. HTTP 长连接短连接使用场景是什么
- **长连接**：短且频繁的请求（如网页上有大量图片、CSS及经常交互的 REST API 前后端分离），复用连接能加快速度减小开销。
- **短连接**：偶尔的、耗时长的请求或不需要并发支持的场景；服务提供商为资源控制（不希望单个客户端一直占有线程）。管理简单，处理完就释放。

## 35. HTTP 和 HTTPS 的区别？
- **安全性**：HTTP 是明文传输数据；HTTPS 是经过 SSL/TLS 加密的，更安全。
- **端口**：HTTP 默认使用 80 端口，HTTPS 默认 443 端口。
- **性能开销**：HTTPS 由于需要进行加解密计算与握手机制，比 HTTP 消耗更多服务器和客户端资源与耗时。
- **证书限制**：HTTPS 需要向 CA 申请数字证书。

## 36. HTTP 报文常见字段有哪些？
Host、Connection、User-Agent、Accept、Content-Type、Content-Length、Authorization、Cookie/Set-Cookie、Cache-Control。

## 37. HTTPS 是如何保证通信安全的？
利用了 SSL/TLS 协议。主要结合了：
1. **加密**：握手阶段通过非对称加密协商出一个共享的安全秘钥（会话秘钥），后续通信全程使用对称加密保证机密性。
2. **认证**：通过数字证书验证服务端的身份。
3. **完整性校验**：通信数据会被计算摘要（MAC/ Hash），保证内容不被篡改。

## 38. HTTPS 大概过程流程讲一下？
1. 客户端发送 Client Hello（含支持的密码套件和随机数）。
2. 服务端回复 Server Hello（含确认的密码套件、证书、服务端随机数）。
3. 客户端验证证书有效性，然后通过证书里的公钥加密一段"预主密钥"发给服务端。
4. 服务端用私钥解密得到"预主密钥"。
5. 双方利用各自手上的 客户端随机数+服务端随机数+预主密钥共同计算出**对称加密使用的会话密钥**。
6. 后续双方通过会话密钥进行加密的 HTTP 通讯。

## 39. 什么是数字证书？
包含公钥、确保证书持有者身份信息（域名组织机构）、数字签名（由 CA 机构用自己的私钥签写的以防篡改）的数据体。它就像服务器的网络身份证。

## 40. 什么是对称加密、非对称加密？
- **对称加密**：加密和解密使用的是同一把密钥。速度快但在网络传输密钥安全性较弱（如 AES）。
- **非对称加密**：有一对密钥（公钥和私钥）。公钥加密的内容只能由私钥解密，私钥签名的内容可由公钥验证。速度慢，主要用于身份验证和少量关键数据交换（如 RSA）。

## 41. 什么是 Cookie?
Cookie 是服务器发送到用户浏览器并保存在本地的一小块数据，它会在浏览器下次向同一服务器再发起请求时被携带并发送到服务器上。常用于鉴权状态存储。

## 42. 什么是 Session?
Session 是一种服务器端保持会话状态的方案。服务器收到请求，为该用户创建唯一的 Session ID 和对应的数据区并在服务端保存（内存或Redis等），同时将 Session ID 返回客户端（通常附着在 Cookie中）。

## 43. cookie和session是怎么实现用户的登录状态的？
1. 用户首次登录向服务器提交账号密码验证。
2. 验证通过后，服务器为该用户生成一个唯一的 Session ID，并记录相关用户信息。
3. 服务端在响应包头中通过 Set-Cookie: JSESSIONID=xxx 返回给浏览器。
4. 将来浏览器每次发请求时通过包头带着这个 Cookie。服务器通过识别 Cookie 里的 Session ID 在服务器内部找到对应的登录状态，从而判定用户已登录过。

## 44. cookie和session有什么区别？
- **存储位置**：Cookie 存在浏览器客户端侧；Session 存在服务器存储区。
- **安全性**：Session 安全性高于 Cookie，Cookie 里的内容可能被窃取篡改，而 Session 核心数据保留在服务器，客户端只有一串 ID。
- **存储容量**：单个 Cookie 一般受限于 4KB；Session 存储量极大限制于服务器资源。
- **性能消耗**：Session 全部存放在服务端并发量大时会增加服务器压力；Cookie 在每次请求都要发送，占宽带。

## 45. UDP 如何实现可靠传输？
需要在 **应用层** 参照 TCP 实现机制重新造轮子。一般涉及：
1. 添加序号/序列号确认机制（如 ACK 应答）。
2. 引入超时重传定时器。
3. 加入滑动窗口与拥塞控制。
（典型的应用有 KCP、QUIC协议的前身）。

## 46. URI和 URL之间的区别
- **URI**：统一资源标识符，指明资源身份。它是一个抽象概念，只要能唯一标识一个资源即可。
- **URL**：统一资源定位符，不仅指示资源的代号，还指明了应该怎样找到该资源（如 http://xxx，ftp://xxx 等）。URL 是 URI 的子集，URL一定是 URI，URI 不一定是 URL。

## 47. 什么是ICMP协议？
ICMP（互联网控制报文协议）工作在网络层，它用于在 IP 主机、路由器之间传递控制消息和差错报告（如目的不可达、超时、重定向等）。它封装在 IP 数据报中发送。

## 48. ICMP 有哪些实际应用，举几个例子？
1. **Ping 命令**：通过发送 ICMP Echo Request/Reply 报文测试两个主机的连通性。
2. **Traceroute 命令**：利用 ICMP 超时报文和目的不可达报文探测到达目的地经过的路由器路径。

## 49. IPV4 地址不够如何解决
1. **NAT (网络地址转换) / 局域网**：允许多个内部设备通过同一个公网 IP 分享对外通信，大幅节约 IP。
2. **CIDR 与 VLSM**：对 IP 地址池进行无分类编址与变长子网掩码划分，减少地址浪费。
3. **DHCP**：动态主机配置，仅对在线的电脑分配 IP，避免闲置占用。
4. **推进 IPv6**：根本解决方案。地址长度高达 128 位，能给地球上每一粒沙子都分配一个地址。

## 50. 为什么 TCP 建立连接是三次握手，而不是两次或四次？
- **为什么不是两次**：主要是为了防止已失效的连接请求报文段突然又传送到了服务端，从而产生错误。如果是两次握手，服务端收到陈旧的 SYN 就立刻建立连接，会浪费服务端资源。同时，三次握手才能证实双方的接收和发送能力均正常。
- **为什么不是四次**：服务端收到客户端的 SYN 后，可以直接将表示同意连接的 SYN 和确认收到客户端请求的 ACK 放在一个报文里发送，所以合并后只需三次。

## 51. 为什么 TCP 断开连接是四次挥手，而不是三次？
因为 TCP 是全双工通信，发送方和接收方都需要独立关闭自己的发送通道。当服务端收到客户端的 FIN 报文段时，代表客户端不再发送数据，但服务端可能还有数据没发完，所以只能先回发一个 ACK 确认。等到服务端的数据也处理并发送完毕了，才会给客户端发送 FIN 报文。这两个步骤通常不能合并，所以需要四次挥手。

## 52. 什么是 SYN 洪泛（SYN Flood）攻击？如何防御？
- **概念**：攻击者伪造大量的不同 IP 地址，向服务器发送 SYN 包。服务器回复 SYN+ACK 并分配资源建立半连接队列。由于源 IP 是伪造的，服务器永远等不到第三次握手的 ACK，导致半连接队列被占满，正常用户无法建立连接。
- **防御**：
  1. 启用 `SYN Cookie`：服务器收到 SYN 后不立即分配资源，而是计算出一个 Cookie 值作为初始序列号回复，等收到对应的 ACK 后再分配资源验证。
  2. 减少 SYN+ACK 断线重传次数。
  3. 增加半连接队列(`tcp_max_syn_backlog`)的大小。

## 53. 详细讲一下 TCP 的拥塞控制机制
拥塞控制是一个全局性的过程，目的是防止过多的数据注入到网络中。TCP 拥塞控制主要有四个核心算法：
1. **慢开始（Slow Start）**：连接建立初期，拥塞窗口 cwnd 从 1 开始，每收到一个 ACK，cwnd 加倍（指数增长）。
2. **拥塞避免（Congestion Avoidance）**：当 cwnd 达到慢开始门限 ssthresh 时，转为拥塞避免算法，cwnd 按照线性规律缓慢增长，避免网络过载。
3. **快重传（Fast Retransmit）**：当接收方收到乱序报文时，连续发送三个重复的 ACK。发送方收到 3 个连续的重复 ACK 时，不等超时定时器触发，立即重传丢失的报文。
4. **快恢复（Fast Recovery）**：配合快重传使用，将 ssthresh 和 cwnd 减半，然后直接进入拥塞避免状态（线性增长），而不是回到慢开始。

## 54. 服务器上出现大量的 CLOSE_WAIT 状态，是什么原因？
`CLOSE_WAIT` 状态发生在被动关闭方收到 FIN 并回复 ACK 之后。此时处于半关闭状态。
出现大量 `CLOSE_WAIT` 通常是因为**服务端代码缺陷**：服务端业务死锁、阻塞，或者业务逻辑处理完后**没有及时调用 `close()` 关闭 Socket**，导致状态无法推演到 LAST_ACK。

## 55. HTTP 的 Keep-Alive 和 TCP 的 Keepalive 有什么区别？
- **HTTP 的 Keep-Alive**：由应用层实现，目的是**连接复用**。让 TCP 连接在发送完一个 HTTP 响应后不立即断开，以便同一个机器后续的 HTTP 请求重用此连接，减小连接建立/销毁的开销。
- **TCP 的 Keepalive**：由传输层（操作系统内核）实现，目的是**探测连接的健康状态（保活）**。在连接空闲一段时间后，发送探测报文检测对端是否还存活。

## 56. 什么是 CSRF 攻击？如何防御？
- **概念**：CSRF（跨站请求伪造）指攻击者诱导受害者进入第三方网站，在第三方网站中向被攻击网站发送跨站请求。利用受害者在被攻击网站已获取的注册凭证（如自动携带的 Cookie），绕过后台的用户验证，冒充用户执行操作。
- **防御**：
  1. 使用 CSRF Token 校验：服务端渲染时生成一段不可伪造的随机 Token 放进页面，每次请求必须携带该 Token 进行校验。
  2. 校验 HTTP Referer / Origin 字段，判断请求来源是否合法。
  3. 设置 Cookie的 `SameSite` 属性为 Strict/Lax，防止跨站发送 Cookie。

## 57. 什么是 Token (如 JWT)？它和 Session 有什么区别？
- **Session**：状态保存在服务器，客户端凭借 Session ID（通常存在 Cookie 里）来访问。服务端在集群环境下需要做 Session 共享（如使用 Redis）。
- **Token (JWT, Json Web Token)**：无状态身份验证模型，所有用户信息和签名被加密后放在 Token 中，保存在客户端。服务端无需存储状态，只需用相同的密钥解密验签即可。天然适配分布式微服务架构，但 Token 签发后服务端较难主动吊销（除非引入中间件/黑名单机制）。

## 58. 什么是 WebSocket？它和 HTTP 有什么关系？
- **概念**：WebSocket 是基于 TCP 的应用层全双工网络协议。允许浏览器与服务器双向长连接互通信（服务器可以主动发消息给客户端），非常适合实时通信。
- **联系**：WebSocket 建立连接握手时依赖 HTTP 协议（发送带有 `Upgrade: websocket` 头的 HTTP 请求），握手成功后通信就与 HTTP 无关了，转为使用 WebSocket 协议专有的数据帧。

## 59. 几种网络连接异常断开的情况：进程崩溃、断网、宕机
- **进程崩溃**：操作系统内核会介入并负责回收进程占用的网络资源（Socket）。内核会主动发送 FIN 报文给对端，正常走四次挥手流程。
- **断网 / 拔网线**：如果没有数据交互，双方都不知道已断网。直到有数据发送时，会因为收不到 ACK 产生超时重传，到达最大重传次数后 RST 断开；如果一直没有数据交互，依靠 TCP Keepalive 心跳超时检测到断开。
- **服务器宕机 / 断电**：与拔网线类似，来不及发送任何通知。若是带电重启恢复后，收到对端发来的报文，由于本地此时已不存在之前的连接上下文结构，会直接回复 RST 报文重置连接。

## 60. 简述 socket 编程中 `socket()` 函数的核心参数及含义？
`int socket(int domain, int type, int protocol);`
- **domain（协议族）**：指定通信所用的协议族。常用的有 `AF_INET`（IPv4）、`AF_INET6`（IPv6）、`AF_LOCAL` / `AF_UNIX`（本机进程间通信）。
- **type（套接字类型）**：指定通信类型。常用的有 `SOCK_STREAM`（提供面向连接的稳定数据传输，即 TCP）和 `SOCK_DGRAM`（提供数据报服务，即 UDP）。还有一种是 `SOCK_RAW`（原始套接字，可以直接操作 IP 层）。
- **protocol（协议类别）**：通常设置为 `0`，表示由操作系统根据 `domain` 和 `type` 自动选择合适的协议（如 AF_INET + SOCK_STREAM 默认选中 TCP）。

## 61. 详细说说 `listen()` 函数的 `backlog` 参数的作用？（半连接队列与全连接队列）
`int listen(int sockfd, int backlog);`
在 Linux 内核中，TCP 协议栈为每个处于 LISTEN 状态的 Socket 维护了两个队列：
1. **半连接队列（SYN Queue）**：存放收到客户端 SYN 但还未完成三次握手的连接。
2. **全连接队列（Accept Queue）**：存放已经完成三次握手，等待被应用层 `accept()` 取走的连接。
- **backlog 的含义**：在早期的 Linux 中，`backlog` 代表半连接队列和全连接队列的总和。而在 Linux 2.2 之后，`backlog` **主要用于指定全连接队列（Accept Queue）的最大长度**（实际长度还受内核参数 `somaxconn` 限制，取两者较小值）。如果全连接队列满了，新的连接请求通常会被直接丢弃或忽略。

## 62. `accept()` 函数返回的是什么？它和原来的监听套接字有什么区别？
`int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);`
- `accept()` 成功后会从处于 ESTABLISHED 状态的全连接队列中取出一个连接，并返回一个新的套接字文件描述符（**已连接套接字**），用于与该客户端进行数据的内核级收发（`read/write` 或 `send/recv`）。
- **区别**：原来的 `sockfd` 是**监听套接字**，只负责被动监听客户端的 TCP 连接请求；而 `accept()` 返回的**已连接套接字**代表了一个已经建立好的真实 TCP 通信通道（包含了四元组：唯一确定的 源IP、源端口、目的IP、目的端口）。一个服务器通常只有一个监听套接字，但会有多个已连接套接字。

## 63. 服务器重启时经常报错 `Address already in use`，原因是什么？如何解决？
- **原因**：当服务器主动关闭连接或异常崩溃退出时，其监听端口上的 TCP 连接会进入 `TIME_WAIT` 状态，该状态默认会持续 2MSL（约 1~2 分钟）。在此期间，内核依然认为该端口被占用，导致服务器立刻重启后执行 `bind()` 调用时失败。
- **解决办法**：在调用 `bind()` 之前，通过 `setsockopt()` 为监听套接字设置 **`SO_REUSEADDR`** 选项。该选项告诉内核，如果指定的端口只被处于 `TIME_WAIT` 状态的连接占用，允许当前的监听套接字强行绑定并重用该端口。
```c
int opt = 1;
setsockopt(sockfd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
```

## 64. `send()` 和 `recv()` 函数的返回值含义？如果返回 0 或 -1 代表什么？
- **返回值 > 0**：
  - `send()`：表示成功将多少字节的数据拷贝到了内核的**发送缓冲区**（注意：这不代表数据已经成功发送到网络上甚至对端）。
  - `recv()`：表示成功从内核的**接收缓冲区**读取了多少字节的数据到应用层的 Buffer 中。
- **返回值 == 0**：
  - 通常出现在 `recv()` / `read()` 中，表示**对端已经正常关闭了连接（发送了 FIN 报文）**，即读到了 EOF。此时本端应该进行资源清理，停止读写，并调用 `close()` 关闭套接字。
- **返回值 == -1（即 < 0）**：
  - 表示发生了错误或特殊事件，具体原因需要检查全局变量 `errno`。
  - **特例（非阻塞 Socket）**：如果 socket 被设置为了非阻塞模式，且 `errno` 为 `EAGAIN` 或 `EWOULDBLOCK`，说明此时缓冲区已满（写操作）或为空（读操作），这并非严重的网络错误，只是提示现在还不具备读写条件，配合 epoll 等待下一次就绪即可。如果是 `EINTR`，表示系统调用被信号中断，通常可重新调用。
