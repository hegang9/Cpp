# 计算机网络面试常考场景题与解答

## 1. 经典场景：从浏览器中输入 URL 到页面显示，经历了什么过程？
**回答要点：**
1. **URL解析**：验证URL合法性，提取协议、域名、端口和路径等信息。
2. **DNS解析**：按顺序查询浏览器缓存、操作系统缓存(hosts文件)、路由器缓存、本地域名服务器(ISP)，最后递归/迭代查询根域名服务器、顶级域名服务器和权威域名服务器，获取目标IP地址。
3. **建立TCP连接（三次握手）**：客户端发送SYN，服务端回复SYN+ACK，客户端再发送ACK。若是HTTPS协议，在此之后还会进行TLS/SSL握手建立加密通道。
4. **发送HTTP/HTTPS请求**：浏览器组装HTTP请求报文（请求行、请求头、空行、请求体）并发往服务器。
5. **服务器处理请求并返回**：服务器接收请求，由后端应用处理后，返回HTTP响应报文（状态行、响应头、空行、响应体）。
6. **浏览器渲染页面**：
   - 解析HTML生成DOM树。
   - 解析CSS生成CSSOM树。
   - 将DOM树和CSSOM树结合生成渲染树（Render Tree）。
   - 布局（Layout/Reflow），计算每个节点的几何信息。
   - 绘制（Paint/Repaint），将像素绘制到屏幕上。
7. **断开连接（四次挥手）**：数据传输完毕后，双方通过四次挥手断开TCP连接。

## 2. 场景题：服务器出现大量的 TIME_WAIT 状态，可能是什么原因？如何解决？
**回答要点：**
**原因：**
TIME_WAIT 是 TCP 四次挥手中主动关闭连接方必然经历的状态。大量出现通常是因为服务器作为主动关闭方，处理了大量短连接（如高并发的HTTP短连接）。每个连接结束后都要保持 `2MSL`（通常是60秒）的 TIME_WAIT 状态，导致占用大量端口和内存资源。

**解决办法：**
1. **开启复用和快速回收**：修改Linux内核参数（`sysctl.conf`）：
   - `net.ipv4.tcp_tw_reuse = 1`：允许将 TIME-WAIT sockets 重新用于新的 TCP 连接。
   - `net.ipv4.tcp_tw_recycle = 1`：加速 TIME-WAIT sockets 的回收（NAT环境下需谨慎，Linux 4.12后已被移除）。
2. **长连接替代短连接**：在HTTP请求头中添加 `Connection: keep-alive`，或者使用 WebSocket/HTTP2 等复用连接的技术。
3. **增加端口范围**：调整 `net.ipv4.ip_local_port_range`，增加可用临时端口。
4. **缩短 TIME_WAIT 时间**：调整 `net.ipv4.tcp_max_tw_buckets`（系统同时保持TIME_WAIT套接字的最大数量），超过该值会直接销毁并打印警告。

## 3. 场景题：如何基于 UDP 实现可靠传输？（如 KCP/QUIC 的设计思想）
**回答要点：**
UDP本身无连接且不可靠，要在应用层实现可靠传输，需要引入类似TCP的机制：
1. **序列号和确认应答（ACK）**：发送端为每个数据包编号，接收端收到后返回ACK。
2. **超时重传**：发送方启动定时器，如果在规定时间内未收到ACK，则重新发送该数据包。
3. **滑动窗口与流量控制**：限制发送方的数据发送速率，避免压垮接收端。记录接收窗口大小。
4. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复机制，根据网络状况动态调整发送速率。
5. **前向纠错（FEC）**：发送数据时增加冗余纠错码，接收端如果有少量数据包丢失，可以通过冗余数据直接恢复，减少重传延迟（QUIC早期特性）。

## 4. 场景题：TCP 粘包和拆包现象是怎么产生的？如何解决？
**回答要点：**
**产生原因：**
TCP 是面向字节流的协议，没有消息边界。
- **粘包**：发送方发送的多个小数据包被TCP底层合并成一个大数据包发送（Nagle算法）；或接收方应用层读取不及时，导致多个包堆积在接收缓冲区。
- **拆包**：发送方的数据包大小大于TCP发送缓冲区剩余空间或大于MSS（最大报文段长度），数据包被拆分为多个部分发送。

**解决策略（应用层处理）：**
1. **消息定长**：每个数据包固定长度，不够的空格补齐。
2. **特定分隔符**：在数据包末尾增加特定字符（如 FTP 的 `\r\n`），接收端通过分隔符划分报文。
3. **消息头加消息体**：在消息头部加上表示消息长度的字段（Length Field）。接收端先读取头部获取长度，再根据长度读取消息体内容。（最常用、最稳定的方案）

## 5. 场景题：如果客户端突然断电或者网线断开，服务器是怎么知道的？
**回答要点：**
如果没有任何数据传输，TCP连接双方是无法立刻察觉到断电或断网的（处于半打开状态，Half-Open）。
**感知方式：**
1. **TCP KeepAlive（保活机制）**：操作系统层面自带的机制。若经过一段时间（默认2小时）没有数据交互，TCP会自动发送探测报文。如果连续探测（默认9次）未收到响应，则认为连接断开。但是默认时间太长，不适合实时性要求高的场景。
2. **应用层心跳机制（Heartbeat）**：客户端或服务端在应用层定时（如每隔5秒）发送轻量级心跳包（Ping），另一端回复响应（Pong）。若在设定超时时间内未收到心跳响应，则主动断开连接，释放资源。这比TCP KeepAlive更灵活且能检测应用层死锁。

## 6. 场景题：你要设计一个文件断点续传功能，需要用到 HTTP 的哪些特性？
**回答要点：**
断点续传主要依赖于 HTTP 的 **范围请求（Range Request）** 机制。
1. **检查服务端支持**：客户端先发起 HEAD 或 GET 请求，看响应头中是否包含 `Accept-Ranges: bytes`。
2. **请求特定范围**：如果支持断点续传，客户端在发请求时通过头部指定请求的字节范围，例如 `Range: bytes=500-1000`（请求第500到1000字节）。
3. **服务端响应**：服务端返回 `206 Partial Content` 状态码，并在响应头中包含 `Content-Range: bytes 500-1000/2000`（表示当前返回范围和文件总大小），随后返回对应的数据。
4. **文件一致性校验**：结合 `ETag` 或 `Last-Modified` 头部，防止在断点续传期间服务器上的文件被修改。如果有变动，需重新从头下载。

## 7. 场景题：如何解决跨域（CORS）问题？
**回答要点：**
跨域是因为浏览器的**同源策略**（协议、域名、端口三者必须全部相同）造成的安全限制。
1. **CORS（跨域资源共享）**：官方标准解决方案。服务端在响应头中设置 `Access-Control-Allow-Origin: *`（或指定的域名），以及对应的方法和头部允许。对于非简单请求，浏览器会先发送 HTTP `OPTIONS` 预检请求（Preflight）。
2. **JSONP**：利用 `<script>` 标签没有跨域限制的漏洞，只能解决 GET 请求。
3. **Nginx 反向代理**：在同源的服务器上配置 Nginx 将请求代理转发给不同源的后端接口。浏览器感知到的依然是同源请求。
4. **WebSocket**：WebSocket 协议自带支持跨域，建立连接后不受同源策略限制。

## 8. 场景题：如果服务器遭到了 SYN Flood 攻击（DDoS），该如何防御？
**回答要点：**
**攻击原理：**
攻击者伪造大量的随机源 IP 地址，向服务器发送大量 TCP SYN 报文。服务器回复 SYN+ACK 并分配资源进入 SYN_RECV 状态，但因为源 IP 是伪造的，永远等不到最后一次 ACK。这就导致服务器的半连接队列（Half-Open Queue）被打满，无法处理正常用户的连接请求。

**防御方案：**
1. **开启 SYN Cookie（最常用）**：修改内核参数 `net.ipv4.tcp_syncookies = 1`。当半连接队列满时，服务器不再立即分配资源，而是根据源地址、目的地址、时间戳等计算出一个加密的 Cookie 作为初始序列号发回去。正常的客户端会把这个 Cookie 加 1 发回 ACK，服务器此时再验证并分配资源建立连接。
2. **缩短 SYN Timeout 时间**：降低 `SYN+ACK` 的重传次数和超时时间，让半连接更快被释放。
3. **增加半连接队列大小**：修改 `tcp_max_syn_backlog` 参数，扩大队列容量（治标不治本）。
4. **前端部署防火墙/高防IP**：利用云服务商的 Web 级应用防火墙、CDN 或高防 IP 节点进行恶意流量清洗。

## 9. 场景题：HTTPS 的连接过程是怎样的？它是如何保证安全的？
**回答要点：**
HTTPS = HTTP + SSL/TLS。结合了非对称加密、对称加密、散列（哈希）算法和数字证书。

**连接过程（以常见非对称加密交换密钥的 RSA 握手为例）：**
1. **Client Hello**：客户端发送支持的 TLS 版本、加密组件列表（Cipher Suites）和一个随机数 `Client_Random`。
2. **Server Hello & Certificate**：服务端回复选定的加密组件、服务端随机数 `Server_Random`，并发送服务端的**数字证书**（其中包含服务端的公钥和 CA 的签名）。
3. **证书验证**：客户端通过操作系统/浏览器内置的 CA 根证书公钥，验证服务端证书签名的合法性（是否被篡改、是否过期、域名是否匹配等）。
4. **生成共享密钥**：验证通过后，客户端生成一个随机的预主密钥（`Pre-Master Secret`），并用**证书里的服务端公钥对其进行非对称加密**后发送给服务端。
5. **服务端解密**：服务端用自己的**私钥解密**得到 `Pre-Master Secret`。至此双方都拥有了完整的三个参数：`Client_Random`、`Server_Random` 和 `Pre-Master Secret`。通过相同的算法生成最终的**会话密钥（Master Secret）**。
6. **加密通信开始**：双方互发 `Finished` 消息（用生成的会话密钥加密一段握手校验数据），握手结束。之后客户端与服务端的全部 HTTP 请求响应，都会使用该**会话密钥进行对称加密**传输。

## 10. 场景题：TCP 为什么要三次握手？两次不行吗？四次不行吗？
**回答要点：**
- **为什么不能是两次？**
  最核心的目的是**防止已失效的请求连接报文段又突然传到服务端，造成服务端资源浪费**。
  假设只进行两次握手：客户端发送的第一个 SYN 报文在网络节点中滞留，客户端超时后重发并完成了两次握手建立通信、随后断开。此时旧的滞留 SYN 报文突然到达服务端，服务端以为是一次新的请求，回复 SYN+ACK 并直接进入 ESTABLISHED 状态分配了内存等资源。但客户端处于等待状态不会理会，导致服务端死等并一直浪费这部分连结资源。
- **为什么不能是四次？**
  三次握手已经能充分确认双方的发送能力和接收能力正常：
  - 第 1 次（SYN）：服务端确认客户端能发；
  - 第 2 次（SYN+ACK）：服务端发给客户端，客户端收到，得出结论服务端能接收且能发送；
  - 第 3 次（ACK）：服务端收到后确认客户端能接收。
  其实第二步服务端的 SYN 和 ACK 是可以分开成两次发送的（这就变成四次握手），但合并成一个包同时发送效率更高，所以拆成四次属于多此一举。

## 11. 场景题：HTTP/1.1、HTTP/2、HTTP/3 解决了哪些场景的核心问题？
**回答要点：**
- **HTTP/1.1**：默认开启了长连接（Keep-Alive）。解决了 HTTP/1.0 每次请求都要重新进行 TCP 三次握手的建立和四次挥手的性能损耗。
  - **痛点**：存在**应用层的队头阻塞（Head of Line Blocking）**，即使使用了 Pipeline 机制，在同一 TCP 连接中，响应也必须严格按照请求的顺序返回。同时头部未经压缩，开销大。
- **HTTP/2**：引入了**多路复用**机制（通过完全的二进制分帧和 Stream 流 ID 管理）。多个请求可以乱序混合在一个 TCP 连接上并发发送，接收端根据 ID 组合，彻底解决了**应用层的队头阻塞**。还增加了 HPACK 头部压缩和服务器推送功能。
  - **痛点**：因为底层仍依赖 TCP，TCP 是按序字节流交付的。如果某一个包在网络中丢失，TCP 滑动窗口就会停下来重传该包，导致同一连接中后续所有 Stream 的数据也被阻塞在内核层里，这被称为**TCP层的队头阻塞**。
- **HTTP/3**：底层彻底抛弃了 TCP，改用 **UDP + QUIC** 协议。QUIC 在 UDP 之上自己重写并实现了加密握手、拥塞控制和重传机制。
  - **突破**：不同 Stream 在 QUIC 里是真正独立的，丢某一个流的包只会令那一个流等待重传，不再影响其他流的数据合并，彻底解决了所有层次的队头阻塞。且由于整合了 TLS 和 QUIC 各自的加密建立机制，实现了极致的 0-RTT/1-RTT 快速连接建立。

## 12. 场景题：如何实现单点登录（SSO）？Session 方案和 Token 方案应该选哪个？
**回答要点：**
在现在的分布式/微服务演进场景中，经常面临用户的跨系统跨域登录状态问题。
- **Session 方案**：
  传统方式将会话保存在服务端内存。对于微服务场景需要引入 Redis 等集中式缓存进行 Session 共享（Spring Session）。
  - **优点**：服务端掌控力强，可以随时在集中缓存中令某个 Session 过期，实现主动踢人下线。
  - **缺点**：每次请求都要去查询缓存，增加额外开销；集群要维护这个庞大的缓存组件，扩展性相对于纯无状态稍差。
- **Token 方案 (如 JWT - JSON Web Token)**：
  服务端不保存任何状态，只在用户验证密码成功时签发一段携带用户信息、并由私钥签名的 Token 字符串抛给前端。前端每次请求放入 `Authorization: Bearer <Token>` 头部带上，后端拦截器使用公钥验签正常即可放行。
  - **优点**：服务端完全**无状态**，天生容易水平扩展，不需要担心分布式部署的会话一致性；避开了 CSRF 攻击；对跨域十分友好。
  - **缺点**：Token 一旦下发，要想让它立刻**主动失效非常困难**。通常只能靠 Token 自身存放的时间自然过期，如果被盗用这期间无法补救（除非结合 Redis 做黑名单校验，但那又退化成了有状态的系统）。且 JWT 不应该保存大量数据，否则会造成头部体积过于臃肿消耗网络带宽。
- **SSO 主流实现套路（如 OAuth2.0、CAS）**：
  公司提供一个核心独立的集中认证中心（SSO-Server）。各业务系统拦截到未登录时，跳转重定向到认证中心的登录页；认证中心登录成功后带着票据（Ticket）或 Auth-Code 再次回调到原业务系统；业务系统拿着票据去向认证中心换取自身局部的访问 Token，从而各自建立独立的局部会话体系。

## 13. 场景题：局域网内两台主机是如何进行通信的？如果只知道对端 IP 而不知道 MAC 地址会发生什么？
**回答要点：**
主机之间的最终物理链路通信，依赖的是数据链路层的 **MAC 地址**，而不是网络层的 IP。
过程如下（假设主机A向同网段主机B发包）：
1. 主机 A 首先根据本机掩码运算，判定目标 IP 是否跟自己属于同一个子网。如果是同一子网（局域网），进入第 2 步。
2. 主机 A 查看本机的 **ARP 缓存表**，试图寻找该目标 IP 对应的目标 MAC 地址。
3. 若缓存表中没有，主机 A 会向本局域网内广播发送一个 **ARP 协议询问包**：“本局谁的 IP 是 `x.x.x.x`？请把你的 MAC 地址告诉我！”（包中的目的 MAC 地址填的全是 `FF-FF-FF-FF-FF-FF`）。
4. 交换机收到广播帧后向局域网除发送方外的所有的端口进行泛洪泛滥发出去。局域网内所有主机都会收到这个 ARP 询问。
5. 其他主机收到后解封装看目标 IP 发现不是自己，静默丢弃；而主机 B 发现目标 IP 正是自己本机 IP，就向主机 A 发送 **ARP 单播响应**包，附上自己的 MAC 地址。
6. 主机 A 收到响应，将新的 IP-MAC 映射写入 ARP 缓存表。
7. 最后，主机 A 用这个获取到的目标 MAC 地址将原始的数据封包组装成以太网数据帧结构，真正发送出去，完成了内网直接通信。
*(扩展：如果是跨网段通信，ARP 询问过程中的目标 IP 就会被替换为您本机设置好的**默认网关（路由器局域网口IP）**，数据包会由局域网发到路由器，由路由器代为跨网域寻址转发)*

## 14. 场景题：当你使用 Ping 命令时，背后发生了什么事情？
**回答要点：**
`ping` 是基于网络层的 **ICMP 协议**（Internet Control Message Protocol，互联网控制消息协议），它是不用基于任何传输层协议（它没有端口号概念，不经过 TCP 或 UDP）而直接包裹在 IP 层数据包中的协议。
**工作过程：**
1. 客户端使用 DNS 解析目标主机的 IP 地址。
2. 构造一个 ICMP 的 **Echo Request（回显请求）** 数据包，包中包含标识符、序号（Seq）以及记录当前的时间戳等数据，传递给 IP 层封装后发送。
3. 途径路由器时如果 TTL 值为 0（超过了最大跃点数），或者目标不可达，路由器会发回对应的 ICMP 错误报告报文（如 Time Exceeded、Destination Unreachable）。
4. 如果数据包成功到达目标主机，目标主机会原样回应一个 ICMP 的 **Echo Reply（回显应答）** 报文。
5. 客户端收到后，检查序号和标识符，提取当时发包时写下的时间戳并与当前收包时间相减求出 RTT（往返时延），完成一次探测。

## 15. 场景题：请聊一聊 Cookie、Session、Token 以及 JWT 之间的区别和关系。
**回答要点：**
这是一个面试非常高频率和开放性的体系问题。
- **Cookie 是什么**：是由于 HTTP 本身是无状态的，浏览器用来存储少量信息及会话追踪的手段。由服务端在 `Set-Cookie` 中下发，客户端每次后续请求带在头部 `Cookie: xx=yy` 中，最大 4KB。存在 CSRF（跨站请求伪造）的风险，可以通过 SameSite 属性控制。
- **Session 是什么**：会话控制的概念模型及对应服务器内存中保存的具体状态数据（类似一张哈希表）。通常，Session 强依赖于 Cookie 中保存的一个字符串 `JSESSIONID` / `PHPSESSID` 来在每次握手时从缓存中查询该用户在服务器上的对应状态信息。
- **Token / JWT 是什么**：Token 是抽象泛指客户端的一个"身份令牌"，它既可以是一长串随机字符串（拿着字符串依然要去查 Redis），也可以是自包含所有数据的 **JWT（JSON Web Token）**。JWT 中由于携带了被私钥进行 HMAC-SHA256 后签署生成的 Signature 防串改签名数据，只要签名验证正确就能判定该用户信息确实是由自己这个系统颁发的，从而做到把状态交给客户端而服务端不用存，实现了服务端的**无状态水平扩展**。这也是它们与传统 Session 设计思想的最本质不同区别。
