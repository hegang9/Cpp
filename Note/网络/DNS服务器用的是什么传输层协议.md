# DNS服务器使用的传输层协议

DNS（域名系统）在传输层**同时使用了 UDP 和 TCP 两种协议**，且默认端口均为 **53**。

之所以同时支持这两种协议，是为了在**解析效率**和**数据可靠性**之间取得平衡。它们在不同的场景下发挥各自的优势：

## 1. 为什么主要使用 UDP？（客户端日常查询）

在绝大多数日常的客户端域名解析查询中，DNS 优先甚至只使用 UDP 协议。

*   **极高的效率与速度**：DNS 查询通常只是一个非常简短的问答（例如“www.baidu.com 的 IP 是多少？” -> “是 110.242.68.3”）。如果使用 TCP，每次查询都需要经过“三次握手”建立连接和“四次挥手”断开连接，这会产生巨大的网络开销和延迟。UDP 是无连接的，发出请求后立刻就能收到响应，非常迅速。
*   **降低服务器负载**：全球有海量的 DNS 查询请求，如果全面采用有状态的 TCP，会导致根域名服务器和顶级域名服务器承受灾难性的并发压力。UDP 的无状态特性极大地释放了服务器的资源。
*   **数据包小**：传统的 DNS 查询和响应的数据包都非常小，通常远小于 UDP 的最大安全报文长度（早期的标准限制响应包大小在 **512 字节** 左右）。

## 2. 为什么还要使用 TCP？（区域传送与大包响应）

既然 UDP 那么好，为什么还需要用 TCP 呢？主要是在以下两种核心场景下必须转为或直接使用 TCP：

### 场景一：区域传送（Zone Transfer）
*   DNS 服务器之间（例如主域名服务器和辅助域名服务器之间）需要进行数据同步备份。这种操作叫做“区域传送”。
*   在区域传送时，要同步的数据量非常庞大，远远超过了 UDP 的承载能力。
*   同时，区域传送要求保证数据的**绝对准确和完整**，不能有任何丢失。TCP 提供了可靠的字节流传输、错误控制和重传机制，非常适合这种大文件传输场景。

### 场景二：响应数据包过大（超过 512 字节引发截断）
*   当客户端使用 UDP 发起查询时，如果服务器发现自己要返回的响应信息（例如包含大量的 IPv6 地址 AAAA 记录，或者复杂的 DNSSEC 安全校验信息）太长，超出了传统的 **512 字节** 限制。
*   服务器依然会用 UDP 返回一个包，但在响应头中会把 **`TC` (TrunCation，截断)** 标志位置为 `1`。
*   客户端收到带有 `TC=1` 的报文后，就会立刻明白：“数据太多被截断了”。于是客户端会**主动切换到 TCP 协议**，向服务器的 53 端口重新发起完整的查询，以保证能拿到全部、完整的解析结果。

---

## 总结
*   **UDP（端口 53）**：用于日常的、标准的、负载小的客户端 DNS 查询（追求极致速度）。
*   **TCP（端口 53）**：用于主从服务器之间的区域传送，以及当客户端发现 UDP 响应被截断（响应报文太大）时回退使用的可靠传输机制（追求大容量和绝对可靠）。
