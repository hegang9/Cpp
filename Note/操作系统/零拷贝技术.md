## 零拷贝技术 (Zero-Copy)

### 1. 什么是“零拷贝”？
零拷贝（Zero-copy）并不是指完全没有任何数据拷贝操作，而是指**避免 CPU 将数据从一块存储拷贝到另一块存储**（通常是指避免数据在“内核空间”与“用户空间”之间来回复制），从而大幅降低 CPU 的上下文切换和数据拷贝开销，提高文件传输、网络发送等场景的数据吞吐量。

### 2. 传统 I/O 方式的痛点
假设我们要实现一个简单的文件下载服务器：将磁盘上的文件读取出来，然后通过网卡发给客户端。
传统代码通常长这样：
```cpp
read(file_fd, buffer, len);
write(socket_fd, buffer, len);
```
在底层，这两行简单的代码会引发极其昂贵的代价：**4 次上下文切换 + 4 次数据拷贝。**

#### 传统 I/O 过程拆解：
1. **用户态 -> 内核态**：发起 `read` 系统调用（第 1 次上下文切换）。
2. **DMA 拷贝（第 1 次拷贝）**：*硬件 DMA* 将数据从**磁盘**复制到内核空间的**内核缓冲区 (Read Buffer/Page Cache)**。
3. **CPU 拷贝（第 2 次拷贝）**：*CPU* 将数据从**内核缓冲区**复制到用户空间的**用户缓冲区 (`buffer`)**。
4. **内核态 -> 用户态**：`read` 返回，切回用户态（第 2 次上下文切换）。数据到了我们代码里。
5. **用户态 -> 内核态**：发起 `write` 系统调用（第 3 次上下文切换）。
6. **CPU 拷贝（第 3 次拷贝）**：*CPU* 将数据从**用户缓冲区**复制回内核空间的**Socket 缓冲区**。
7. **DMA 拷贝（第 4 次拷贝）**：*硬件 DMA* 最后将数据从 **Socket 缓冲区**复制到**网卡引擎**发出。
8. **内核态 -> 用户态**：`write` 返回，全剧终（第 4 次上下文切换）。

**核心痛点**：对于文件下载这种不需要在应用程序里修改数据的场景，把数据从内核“捞”到用户态，再原封不动地“塞”回内核态，不仅纯属多余，而且是极大的 CPU 浪费！

### 3. mmap + write 优化（早期的半零拷贝）
使用 `mmap()` 可以消除传统 I/O 中那次将文件数据读到用户空间的重复 CPU 拷贝。

*   **原理**：`mmap()` 会将用户空间的虚拟内存地址**直接映射**到内核空间的 Page Cache（文件缓冲区）上。
*   **流程**：
    1. 用户程序发起 `mmap`：将文件映射到内存（发生 DMA 拷贝：磁盘 -> 内核 Buffer）。
    2. 用户程序发起 `write`：此时不需要用户态向内核态的数据搬运了，*CPU* 直接将数据从**内核 Buffer** 拷贝到 **Socket 缓冲区**。（这是必须要用 CPU 进行的一次拷贝）。
    3. DMA 从 Socket 缓冲区拷贝到网卡。
*   **收益**：
    *   **上下文切换**：4 次（依然需要调用一次 mmap 和一次 write，均会进出内核）。
    *   **数据拷贝**：3 次（2 次 DMA 拷贝，**仅需 1 次 CPU 拷贝**，少了一次系统内部搬运）。

### 4. 真正的杀器：`sendfile` 系统调用
在 Linux 2.1 内核中引入了 `sendfile()` 这个专门为了“零拷贝”诞生的系统调用。它的语义就是：直接把数据从一个文件描述符传输到另一个文件描述符（往往是 socket），不再经过用户层！

`ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);`

#### sendfile 经历了两个版本的演进：

#### a. Linux 2.1 中的常规 sendfile
*   **流程**：
    1. 发起 `sendfile` 系统调用（1 次陷入内核的上下文切换）。
    2. **DMA 拷贝**：磁盘 -> 内核 Read Buffer。
    3. **CPU 拷贝**：数据在内核中，被 CPU 从**Read Buffer**复制到了**Socket Buffer**。
    4. **DMA 拷贝**：Socket Buffer -> 网卡。
    5. `sendfile` 返回（1 次返回用户的上下文切换）。
*   **综合花销**：2 次上下文切换 + 3 次数据拷贝（1次 CPU 参与）。

#### b. Linux 2.4 及之后的极客版 sendfile (配合 SG-DMA)
为了把最后一次内核里的 CPU 拷贝也消灭掉，现代网卡开始支持 **SG-DMA (The Scatter-Gather DMA，分散/聚集 DMA)** 技术。这意味着网卡可以直接从内核的 Read Buffer 中读取数据，而不需要操作系统专门凑一个连续的 Socket Buffer 喂给它。

*   **终极零拷贝的流程**：
    1. 发起 `sendfile` 调用（1 次上下文切换）。
    2. **DMA 拷贝**：磁盘 -> 内核 Read Buffer。
    3. **CPU 仅仅拷贝元数据（极低开销）**：CPU 仅仅把数据的位置（描述符）和长度等少量信息，写到 Socket Buffer 中。这几乎不耗时。
    4. **SG-DMA 拷贝**：带有 SG 功能的 DMA 直接根据 Socket Buffer 里的“地址索引”，把数据从**内核 Read Buffer** 跨过一切障碍物直接搬进**网卡**！
*   **真正做到了所谓的“零 CPU 拷贝”：**
    *   **上下文切换**：2 次。
    *   **数据拷贝**：2 次（**全是 DMA 硬件代劳，CPU 完全不参与搬运实体数据！这就是真正的 Zero-Copy！**）。

---

### 5. `splice` (管道中继技术)
Linux 2.6.17 引入了 `splice` 系统调用。`sendfile` 虽然好，但往往限制了出参只能是 Socket（早期版本）或者必须有一端是真实的文件。
如果想要在任意两个文件描述符之间进行零拷贝传输，可以使用 `splice`。
*   它利用 Linux 的**管道 (pipe)** 作为中转机制，在底层通过移动内存页指针（而非拷贝数据）的方式来实现真正的零拷贝传递。

### 6. 面试总结（经常被问的对比指标）
| 技术实现 | 上下文切换次数 | CPU 数据拷贝次数 | DMA 数据拷贝次数 | 核心应用场景 |
| :--- | :---: | :---: | :---: | :--- |
| **传统 Read/Write** | 4 次 | 2 次 | 2 次 | 需要在用户态修改/处理数据的普通场景 |
| **mmap + write** | 4 次 | **1 次** | 2 次 | 小文件读写、或者多个进程共享通信 |
| **早期 sendfile** | **2 次** | **1 次** | 2 次 | 早期 Linux 的大文件网络分发（如早期 Nginx） |
| **sendfile + SG-DMA**| **2 次** | **0 次** | 2 次 | **Kafka / RocketMQ / Nginx 的极速大文件传输内核** |
