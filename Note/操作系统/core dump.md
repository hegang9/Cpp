## Core Dump (核心转储)

### 1. 概念
**Core Dump（核心转储）**是指当程序在运行过程中发生异常崩溃或被强行终止时，操作系统将当前程序在内存中的状态（包括**变量值、寄存器状态、堆栈调用信息、内存管理信息等**）导出来，保存到一个文件（通常命名为 `core` 或 `core.<pid>`）中的这一过程。

把 Core Dump 形象地理解为**“车祸现场的快照”**。当程序由于致命错误死掉时，这份快照能让开发人员在事后完美“复盘”，从而查出具体是在哪一行代码、因为什么变量引发的崩溃。

### 2. 发生原因
Core dump 本质上是因为程序执行了严重非法的操作，导致操作系统向进程发送了特定的**终止信号（Signal）**，而这些信号的默认处理行为（Action）之一就是转储核心并终止运行。最常见的原因包括以下几种：

1. **段错误 - 内存非法访问 (SIGSEGV - Segmentation fault)**：*(最常见的崩溃原因)*
   - 解引用空指针（Null Pointer Dereference）。
   - 内存访问越界（如数组下标越界、缓冲区溢出）。
   - 访问已经被释放的内存（野指针 Use-after-free）。
   - 试图往只读内存区域写入数据（如试图修改字符串字面量常量）。
2. **算术错误 (SIGFPE - Floating point exception)**：
   - 最普遍的就是**整数除以零**（Divide by zero）操作。
3. **非法指令 (SIGILL - Illegal instruction)**：
   - 程序指针执行到了非代码段，或代码段被破坏（内存踩踏破坏了指令机器码），导致 CPU 拿到了无法解析的硬件指令。
4. **主动或异常中止 (SIGABRT/SIGIOT)**：
   - 代码中手动调用了 `abort()` 函数。
   - `assert()` 断言失败触发中止。
   - C++ 中抛出了异常但没有被 `catch` 捕获（`std::terminate` 会被调用）。
   - 两次释放同一块内存（Double free）引发堆管理器检测异常从而 `abort`。

### 3. 处理与调试措施
发生 Core dump 后的标准处理流程就是：**获取 Core 文件 -> 使用 GDB 挂载 -> 查看调用栈定位代码**。

#### 第一步：开启 Core 文件生成（配置系统）
Linux 默认通常出于节省磁盘空间的考量，将 Core dump 文件的生成大小限制设置为了 `0`，这意味着即便程序崩溃也不会生成文件。
- 查看当前限制：终端执行 `ulimit -c`
- **放开限制（仅当前终端会话生效）**：`ulimit -c unlimited`
- 如需永久生效，通常需要修改 `/etc/security/limits.conf`。

#### 第二步：确保编译时开启调试信息
为了让调试器能将崩溃时的十六进制内存地址转换成人类可读的**源文件和行号**，编译 C/C++ 程序时**必须**加上 `-g` 参数：
```bash
g++ -g main.cpp -o my_program
```

#### 第三步：确认 Core 文件的位置
程序崩溃后，寻找生成的 core 文件。
早期的 Linux 系统会将它直接扔在程序执行的当前目录下。而现代系统（如 CentOS/Ubuntu）往往会改变其生成位置（通过 `systemd-coredump` 或 `apport` 托管）。
- 可以通过 `cat /proc/sys/kernel/core_pattern` 查看文件是以什么名字、被存储到了哪个路径下。

#### 第四步：使用 GDB 进行事后调试
拿到拥有 `-g` 调试信息的 `可执行文件` 和 `core文件` 后，执行：
```bash
gdb ./my_program ./core
```
进入 GDB 后，通过以下常用命令即可还原案发现场：
1. **`bt` (backtrace) 或 `where`**：打印程序崩溃瞬间的函数调用堆栈！**这是最重要的命令**，可以瞬间看出崩溃是由哪个函数里面的哪一行代码发起的。
2. **`frame <n>` (简写 `f n`)**：切入到 `bt` 打印出来的某一层特定调用栈。
3. **`print <变量名>` (简写 `p var`)**：打印当时在这个函数作用域下的某些变量或指针的值，确认到底是谁等于了 `null` 或者超出了边界。
