## Futex 机制 (Fast Userspace Mutex)

**Futex (Fast Userspace Mutex，快速用户态互斥锁)** 是现代 Linux 系统中实现各种线程同步原语（如 Mutex、条件变量、信号量、读写锁等）的**最核心的底层基石**。

它并非一种可以直接在应用层调用的锁，而是一种**底层机制**，融合了用户态原子访问与内核态睡眠排队的双层架构。

### 1. 为什么需要 Futex？(传统锁的痛点)

在 Futex 诞生之前（Linux 2.5 之前），操作系统的锁实现主要面临两个极端的痛点：

1. **纯内核锁（如早期的 System V IPC 信号量）**：
   无论锁是否存在竞争，每次上锁和解锁都必须发起系统调用（如 `semop`）进入内核态。
   *痛点*：在毫无竞争的大多数情况下，进程依然要付出昂贵的用户态-内核态上下文切换开销，导致并发性能极低。
2. **纯用户态自旋锁（Spinlock）**：
   完全依靠用户态的原子操作 CAS（Compare-And-Swap）死循环抢锁。
   *痛点*：如果锁被长时间占用，等待线程将 100% 霸占并浪费 CPU 资源（烧 CPU）。

为了解决这个矛盾，**Futex 应运而生。它的目标是：无竞争时全在用户态解决（快），有竞争时才求助内核挂起（省 CPU）。**

### 2. Futex 的核心设计思想：双层架构

Futex 的本质是一个**由用户态的“一个 32 位对应的整型变量”（通常是 `std::atomic<int>`）**与**内核态的“一个等待队列”**组合而成的魔法。

1. **Fast Path（快路径 - 用户态无锁抢占）**：
   当线程尝试获取锁时，首先在用户态对那个 32 位整型变量发起原子操作（如 `CAS`）。
   - 如果发现变量空闲，修改成功即代表拿到了锁，**直接返回，完全不需要陷入内核**，性能堪比自旋锁。
   - 如果发现已经被别人占用了，才进入 Slow Path。
2. **Slow Path（慢路径 - 内核态排队睡眠）**：
   在用户态抢不到锁，线程就会发起系统调用 `sys_futex`。向内核报告：“这把锁被占了，请把我加入这个地址对应的挂起队列里，并剥夺我的 CPU 运行权”。

### 3. Futex 核心系统调用解析

Linux 提供了一个非常复杂的系统调用入口：`futex(uint32_t *uaddr, int futex_op, uint32_t val, ...);`

最核心的两个操作指令（`futex_op`）是：

#### a. `FUTEX_WAIT(uaddr, val)`: 挂起排队，防丢失唤醒
- **语义**：检查用户空间地址 `uaddr` 里的值现在是否还是等于 `val`。如果是，则将当前线程挂入内核等待队列，并让出 CPU 睡眠；如果不是，说明值已经被别人改了，系统调用立刻返回 `EWOULDBLOCK`。
- **为什么必须带上 `val` 进行校验？**
  这是为了堵住**“丢失唤醒（Lost Wakeup）”的大漏洞**。
  线程从“发现抢不到锁准备去休眠”到“真正陷入系统去休眠”之间，存在一个时间窗口。如果在这个时间差内，原有的锁持有者释放了锁并发起了唤醒，该线程一旦错过，睡下去后就成了永久假死。Futex 在内核休眠前的最后一刻，对 `uaddr` 的值做二次验证，完美防御了这个竞态问题。

#### b. `FUTEX_WAKE(uaddr, num)`: 唤醒兄弟
- **语义**：唤醒最多 `num` 个挂在 `uaddr` 地址处的线程。
- 通常解锁时，锁的持有者会首先在用户空间使用原子操作修改变量（如由 1 改为 0），随后发现有标志位显示“有人在排队（例如变量为 2）”，此时才会发起 `FUTEX_WAKE(uaddr, 1)` 进入内核，让内核取出一个沉睡的线程将其重新放回就绪队列。

### 4. 示例：用 Futex 打造一把现代 Mutex 锁

下面是现代系统的 Mutex（如 `std::mutex`、`pthread_mutex_t`）底层流转的伪代码：

*定义内部状态状态码：0 = 空闲，1 = 被占用但没人排队，2 = 被占用且有其他人正在阻塞排队*

**Lock 过程：**
```cpp
void lock(int *lock_val) {
    int expected = 0;
    // 1. 尝试 Fast Path，期望它是 0，原子改成 1
    if (CAS(lock_val, expected, 1)) {
        return; // 获取锁成功，由于全程不需要进内核，速度非常快
    }
    
    // 2. 失败了，走 Slow Path。先通过原子操作把它改成 2（宣告不仅被占，还有我在等）
    // 随后调用系统调用 futex 等待
    while (true) {
        expected = *lock_val; // 读取当前状态
        if (expected == 0 && CAS(lock_val, 0, 2)) return; // 刚好空出，抢下
        
        // 发起系统调用休眠：如果 *lock_val 还是 2，就休眠。
        futex_wait(lock_val, 2); 
        // 醒来后继续 while 抢夺
    }
}
```

**Unlock 过程：**
```cpp
void unlock(int *lock_val) {
    // 1. 原子操作扣减。如果原本是 1，变成 0，说明没人在等，Fast Path 结束，直接返回。
    if (atomic_fetch_sub(lock_val, 1) != 1) {
        // 2. 如果本来是 2（说明不仅被占用，而且队列里有沉睡者待唤醒）
        *lock_val = 0;           // 先把锁置空
        futex_wake(lock_val, 1); // 发起系统调用，进入内核态唤醒 1 个等待者
    }
}
```

### 5. Futex 的高级奥义：`FUTEX_CMP_REQUEUE` (防惊群效应)

除了 Wait 和 Wake，Futex 还有另一项绝技：**内核态排队转移（Requeue）**。

在介绍**条件变量 (Condition Variable)** 时，当执行 `notify_all()`（广播唤醒）时，如果暴力的将几十个睡眠的线程同时唤醒，它们立刻都会由于争抢对应的 `Mutex` 锁而再次大面积陷入阻塞！这种现象称为**“惊群效应（Thundering Herd）”**。

`FUTEX_CMP_REQUEUE` 通过在真正唤醒 1 个线程执行外，将其余等待该条件变量地址挂起的 N 个线程，在**内核空间悄悄地重新挂载（转移）到对应 Mutex 的挂起队列上去。**
这使得这些线程依然保持睡眠状态，不需要经历“唤醒进用户态 -> 发现拿不到锁 -> 再次进入内核睡眠”这毫无意义的折腾，极其优雅地解决了高并发性能雪崩问题。

### 总结
1. **Futex = 数据区域 (User space Atomic Integer) + 挂起队列 (Kernel wait queue)。**
2. 它是今天几乎一切高级同步原语之源，**结合了自旋锁的速度与内核锁的节能优势。**
3. 高效的核心在于**快路径（Fast path）能拦截掉绝大多数无竞争情况的资源消耗。**
