## 原子操作

在C++11及以后的版本中，标准库提供了 `<atomic>` 头文件来支持多线程环境下的原子操作。原子操作是不可被中断的操作，在多线程并发访问时，不需要使用互斥锁（Mutex）就能保证数据的一致性和线程安全。原子操作是实现无锁编程（Lock-free programming）的基础。

### 1. 核心类 `std::atomic`

`std::atomic` 是一个模板类，可以封装任意类型的变量，使其所有操作按原子方式执行。

```cpp
#include <atomic>

std::atomic<int> count(0); // 定义一个原子整型变量
std::atomic<bool> flag{false}; // 定义一个原子布尔变量
```

对于常用的基础数据类型，C++ 提供了类型别名，例如：
* `std::atomic_int` 等价于 `std::atomic<int>`
* `std::atomic_bool` 等价于 `std::atomic<bool>`

### 2. 基本操作

* **`store(val)`**：将 `val` 原子地写入。
* **`load()`**：原子地读取当前值。
* **`exchange(val)`**：将值替换为 `val`，并返回旧值。
* **算术和位操作**：支持 `fetch_add`, `fetch_sub`, `fetch_and`, `fetch_or`, `fetch_xor`，也可以直接使用 `++`, `--`, `+=`, `-=` 等重载运算符（对于整型和指针类型）。

### 3. CAS操作 (Compare-And-Swap)

CAS 是无锁编程的核心机制。在 C++ 中，主要提供了两个函数：
* **`compare_exchange_weak(expected, desired)`**：弱版本的 CAS。比较当前值与 `expected`，如果相等，则将其修改为 `desired` 并返回 `true`。如果不相等，则将 `expected` 更新为当前真实值并返回 `false`。由于可能出现“伪失败”（Spurious failure），通常需要放在循环中使用。
* **`compare_exchange_strong(expected, desired)`**：强版本的 CAS。与 weak 版类似，但保证不会出现伪失败，开销可能略大。

```cpp
int expected = 0;
int desired = 1;
// 如果 count 当前是 0，则改为 1，并返回 true
// 如果 count 当前不是 0，则 expected 被修改为 count 的当前值，并返回 false
while (!count.compare_exchange_weak(expected, desired)) {
    // ... 重试或处理失败
}
```

**🔍 什么是“伪失败”（Spurious Failure）？**
* **定义**：即使原子变量的当前真实值等于 `expected` 预期值，`compare_exchange_weak` 操作依然有可能挂掉并返回 `false`。
* **底层硬件原因**：这其实是由处理器的底层架构决定的。
  * **x86 架构**：通常拥有原生的单条 CAS 指令（如 `CMPXCHG` 硬件指令），执行是真正原子的，不容易出现伪失败。
  * **ARM、PowerPC 等 RISC 架构**：由于精简指令集的设计，它们通常没有专门的一条 CAS 指令，而是依靠两条指令组合来实现：**LL/SC（Load-Link / Store-Conditional）**（加载链接/条件存储）。
    * **LL (Load-Link)**：不仅加载内存中的值，还会给这个内存地址建立一个“排他性监视”。
    * **SC (Store-Conditional)**：在把新值写回内存前，检查刚才的“监视”有没有被破坏。如果没有，就写入成功；如果被破坏了，就写入失败。
    * **造成破坏的原因**：如果在 LL 和 SC 指令的间隙中，发生了**操作系统的上下文切换、线程调度、甚至其他线程正好读取/修改了同一个 Cache Line（缓存行）**，SC 指令的安全机制就会判定执行环境不纯洁，从而直接拒绝写入。此时，即使该变量的值根本没有发生任何实质性的改变，CAS 也会宣告失败，这就叫“伪失败”。
* **为什么需要 `weak` 版本？** 既然有不丢数据的 `strong` 版本，为啥还要用 `weak`？
  * `compare_exchange_strong` 为了确保开发者不被伪失败困扰，会在内部悄悄地套一层 `while` 循环，直到发生“真失败（数据对不上）”或“真成功”才返回。
  * 但是，如果你在写无锁数据结构，你的 CAS 代码**通常本来就在一个大的 `while` 循环里**。如果在这层大循环里用 `strong`，就相当于在 ARM 架构上跑了“双重循环”，非常损耗性能。所以这时候直接用能接受伪失败的 `weak` 版，把重试的责任交给外层现成的循环，性能会更好。

### 4. 内存序（Memory Order）

原子操作不仅仅是为了保证单次操作的不可中断性，更重要的是通过**内存序**来解决多线程间的内存可见性和指令重排问题。

**🔍 扩展：指令重排是由 Tomasulo 算法导致的吗？**
你提到的非常准确！但指令重排和不可见性实际上是由**编译期**和**运行期**两层原因共同造成的：

1. **编译器优化重排**：在编译期间，编译器为了极致优化性能，会在不改变**单线程**语义结果（As-if-serial）的前提下，打乱高层代码映射到底层汇编指令的顺序。
2. **CPU 硬件重排（乱序执行 Out-of-Order Execution）**：
   * 正如你所说，现代 CPU 为了充分榨干执行器（ALU、FPU等）算力，普遍采用类似 **Tomasulo 算法** 的动态调度技术。
   * 借助**保留站（Reservation Station）**和 **重排序缓冲区（Reorder Buffer, ROB）**，CPU 允许后续没有数据依赖的指令，越过前面因等待数据（例如 Cache Miss）而卡住等待的指令提前执行。
3. **内存可见性延迟（Store Buffer & Cache）**：
   * 除了指令真的被重排了，CPU 为了缓解核心与 L1 Cache 的速度差，引入了 **Store Buffer（写缓存）** 和 **Invalidate Queue（失效队列）**。
   * 当一个核心修改了变量，可能只写到了自己的 Store Buffer，还没同步回 L1 Cache 或通过 MESI 协议通知其他核心。这导致在其他线程看来，就像是“修改操作被挪到了后面”一样。

**在单线程中，以上机制完全透明且安全；但在多线程场景下，就会导致严重的数据竞争同步BUG。** C++ 定义了 6 种内存模型（`std::memory_order`），主要在底层通过插入各平台对应的**内存屏障（Memory Barrier/Fence）**，来约束编译器和 CPU 的上述重排和缓存行为：

1. **`std::memory_order_relaxed`**（松散模型）：只保证当前操作本身的原子性，不保证线程间的同步，编译器和 CPU 可以自由重排指令。
2. **`std::memory_order_acquire`**（获取模型）：用于读取（Load）操作。保证在本线程中，所有位于该操作之后的内存访问指令都不会被重排到该操作之前。
3. **`std::memory_order_release`**（释放模型）：用于写入（Store）操作。保证在本线程中，所有位于该操作之前的内存访问指令都不会被重排到该操作之后。通常与 `acquire` 配合使用（Acquire-Release 语义）。
4. **`std::memory_order_acq_rel`**（获取释放模型）：结合了 acquire 和 release。用于读取+写入的操作（如 `exchange`）。
5. **`std::memory_order_consume`**（消费模型）：类似 acquire，但仅同步依赖于该原子变量的值的后续操作。由于实现复杂，一般不推荐使用。
6. **`std::memory_order_seq_cst`**（顺序一致性模型）：**默认的内存序**。它是最严格的模型，性能开销最大。不仅保证原子性和同一线程内的重排限制，还保证所有线程看到的所有 `seq_cst` 操作的执行顺序是一致的。

### 5. `std::atomic_flag`

`std::atomic_flag` 是最简单的原子类型，它只保证是无锁的（lock-free），其他类型在某些平台上可能会退化为使用底层锁来实现。它只有两种状态：设置（set）和清除（clear）。常用来实现自旋锁（Spinlock）。

```cpp
std::atomic_flag lock = ATOMIC_FLAG_INIT;

void spinLock() {
    // 当之前的值为 true 时一直循环，直到另一个线程 clear 改为 false
    while (lock.test_and_set(std::memory_order_acquire)) {
        // 自旋等待
    }
}

void spinUnlock() {
    lock.clear(std::memory_order_release);
}
```
