## 条件变量 (Condition Variable)

条件变量是操作系统的并发编程中用于线程同步的一种核心机制。它允许一个或多个线程在某个特定条件不满足时**主动阻塞（挂起）**，直到另一个线程在这个条件发生改变时**唤醒**它们。

条件变量**必须**与互斥锁（Mutex）配合使用，以防止在多个线程检查条件和进入睡眠状态之间发生竞态条件。

### 1. 基本使用

在 C++ 中，可以通过 `<condition_variable>` 头文件中的 `std::condition_variable` 来使用：

```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>

std::mutex mtx;
std::condition_variable cv;
bool ready = false; // 共享的“条件”变量

void wait_thread() {
    std::unique_lock<std::mutex> lock(mtx);
    // 线程会在这里阻塞，直到 ready 变为 true。
    // wait() 内部会自动释放 mtx，并在被唤醒时重新获取 mtx。
    cv.wait(lock, [] { return ready; });
    
    std::cout << "Thread is running, condition is met!\n";
}

void signal_thread() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        ready = true; // 改变条件
    }
    cv.notify_one(); // 唤醒一个等待中的线程
    // cv.notify_all(); // 或者唤醒所有等待中的线程
}

int main() {
    std::thread t1(wait_thread);
    std::thread t2(signal_thread);
    t1.join();
    t2.join();
    return 0;
}
```

#### 为什么需要 Mutex 配合 `wait` 并且要在 `while` 循环（或 `lambda`）中判断？
1. **防止丢失唤醒（Lost Wakeup）**：如果在没有加锁的情况下检查了条件为 `false`，在即将挂起前，另一个线程修改了条件并发送了 `notify`，那么前一个线程就会永远睡死。通过在获取锁的情况下检查条件，保证了“条件检查”和“挂入阻塞队列”对外界来说是原子操作。
2. **防虚假唤醒（Spurious Wakeup）**：操作系统底层（或某些信号异常情况）可能在没有发出 `notify` 的情况下异常唤醒线程。通过 `while (!ready) { cv.wait(...) }` 来强迫线程醒来后再次检查条件是否真正满足。

### 2. 现代操作系统的底层实现原理（以 Linux Futex 为例）

与互斥锁、现代信号量类似，现代 Linux 线程库也是基于 **Futex（Fast Userspace Mutex）** 进行条件变量优化的，并且主要解决从用户态到内核态的竞态问题，以及大规模并发唤醒时的性能问题。

条件变量底层主要维护了一个**等待队列（Wait Queue）及序列号**。（**序列号用来解决丢失唤醒问题**，即释放锁到线程挂起之间的时间窗口可能会被其他线程将条件修改为满足，那么内核会在真正将线程挂起前检查这个序列号是否被修改过，如果被修改过说明条件已经满足了，就不会挂起线程了）

#### a. Wait 操作的底层核心逻辑 (`pthread_cond_wait`)
1. **获取锁**：应用程序调用 `wait(lock)` 前，必须已经拿着对应的 Mutex 锁。
2. **记录状态**：在用户态读取条件变量当前的内部序列号（Sequence Counter）。
3. **解锁、入队并睡眠（原子挂起操作）**：
   释放现有的 Mutex 锁，并调用内核系统调用 `futex(addr, FUTEX_WAIT, ...)` 将本线程挂起。
   **核心难点：从释放锁到陷入睡眠之间存在时间窗口！** 
   *解决方式*：现代 `futex` 会在进入内核休眠前，重新在内核态检查用户态的期望值序列号与当前值是否一致。如果在时间窗口内被改了（说明刚好有人发了 Signal），系统调用就会拒绝挂起当前线程并立即返回，避免了错过唤醒事件（Lost Wakeup）。
4. **被唤醒并重新抢锁**：被唤醒后，线程不能马上继续执行用户逻辑，它会**先重新申请回被它提前释放的锁** `lock(&mutex)`（这里可能会再一次发生普通锁资源的阻塞）。

#### b. Notify(Signal) 操作的底层逻辑 (`pthread_cond_signal`)
1. **修改序列号**：通过原子操作在用户态修改条件变量的计数/序列状态。
2. **唤醒线程**：如果检查到对应的挂起队列中有等待者，通过系统调用 `futex(addr, FUTEX_WAKE, 1)` 陷入内核态，将队列中 1 个等待线程标志为就绪态。

#### c. Notify_All(Broadcast) 的核心优化（Wait Morphing / Requeue）
当调用 `notify_all()` 唤醒所有线程时，如果不做特殊处理，会发生**“惊群效应” (Thundering Herd)**：
大量线程同时从 `futex()` 休眠中醒来，然后**瞬间全部去抢夺同一个 Mutex**。显然只有 1 个线程能抢到，其余几十上百个线程经历了昂贵的“内核态醒来 -> 切换回用户态 -> 发现锁被抢走 -> 再次内核态系统陷入睡眠”的资源浪费。

**现代内核的解决之道：`FUTEX_CMP_REQUEUE`**
为了解决唤醒风暴，Linux 在 `broadcast (notify_all)` 的底层引入了 `REQUEUE` 机制：
- 发生广播时，内核只会真正唤醒 **1 个（或满足条件的极少数）** 线程。
- 对于剩下的线程，内核**不会让它们醒出内核态**，而是**直接在内核空间中**，把它们从“条件变量的等待队列”**平滑地转移（Requeue，也称 Wait Morphing）**到“那个互斥锁（Mutex）的等待队列”中。
- 这样，除了当前能执行的那个线程以外，其余兄弟线程自始至终在内核里安静地睡觉，不会白白去走一遭用户态返回消耗 CPU 时间。极大地提高了高并发场景的吞吐力。
