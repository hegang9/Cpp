# Raft 与 Paxos 算法对比

Raft 和 Paxos 都是分布式系统中用于实现**共识（Consensus）**的核心算法，它们的最终目标是一致的：在存在节点宕机、网络延迟或分区等故障的分布式集群中，保证多个节点的状态机达成强一致性。

尽管目标相同，但它们在设计哲学、可理解性以及工程实现上有着显著的区别。

## 1. 设计初衷与可理解性

*   **Paxos**：由分布式计算的大神 Leslie Lamport 提出，理论基础极其严密且优雅。但是，Paxos 出了名的**难以理解**和**难以实现**。Basic Paxos 只能就单个值达成共识，而要构建实际的系统所需的一系列值共识（Multi-Paxos），Lamport 在早期论文中缺乏详细的实现细节指导，导致业界诞生了各种各样基于 Paxos 变种的系统（如 Chubby, Megastore, Spanner 等），它们在实现细节上往往有很大差异。
*   **Raft**：由斯坦福大学的 Diego Ongaro 和 John Ousterhout 于 2014 年提出。Raft 的首要设计目标就是**可理解性（Understandability）**。为了达到这个目标，Raft 将复杂的共识问题拆解为几个相对独立的子问题：**Leader 选举（Leader Election）**、**日志复制（Log Replication）**和**安全性（Safety）**。

## 2. 核心差异点

### 2.1 领导者（Leader）的地位
*   **Paxos**：在纯粹的 Basic Paxos 中，**没有绝对的 Leader 概念**（任何 Proposer 都可以发起提案）。Leader 的引入（即 Multi-Paxos）仅仅是为了优化性能、解决 Proposer 竞争导致的活锁问题。即使系统中有多个“自认的 Leader”同时提议，Paxos 算法依然能保证安全性，只是性能会退化。
*   **Raft**：**强领导者模型（Strong Leadership）**。Raft 的一切操作高度依赖 Leader。客户端的读写请求都必须通过 Leader，日志只能从 Leader 单向流向 Follower。如果 Leader 宕机，集群的第一要务是停止一切服务，先选举出新的 Leader，然后才能继续处理请求。

### 2.2 日志的顺序与连续性
*   **Paxos**：允许多个 Proposer 并发地在不同的“槽位（Slot）”上发起提议。这意味着 Paxos 的日志提交**可以是乱序的**，日志中可能会出现“空洞（Holes）”。系统需要额外的机制来填补这些空洞。
*   **Raft**：严格要求**日志的顺序性**。Raft 限制了日志的提交必须是连续的，不允许出现空洞。Follower 的日志永远是 Leader 日志的子集（前缀）。新 Leader 产生后，会强制 Follower 复制自己的日志，覆盖冲突的部分。这种单向、连续的追加模型大大简化了系统的状态空间。

### 2.3 选主机制的安全性约束
*   **Paxos**：任何节点都可以尝试成为 Leader。一个落后的节点也有可能成为 Leader，只不过在它提供服务之前，必须先经过一个繁琐的“补课”阶段，把缺失的历史日志通过 Paxos 阶段一补齐。
*   **Raft**：做了一个极其聪明的限制——**只有拥有最完整已提交日志的节点，才能赢得选举成为 Leader**（通过对比 term 和 index）。这保证了 Leader 绝对包含了所有已经确定的历史状态，避免了新 Leader 还需要去向 Follower “问询历史”的复杂逻辑。

## 3. 各种层面的对比总结

| 维度 | Paxos (Multi-Paxos) | Raft |
| :--- | :--- | :--- |
| **设计目标** | 理论的严谨性与普适性 | 极高的可理解性、易于工程实现 |
| **Leader 地位** | 弱领导模型（仅为优化活锁） | 强领导模型（一切以 Leader 为核心） |
| **数据流向** | 可以多点写入，相互合并 | 单向流：绝对由 Leader 流向 Follower |
| **日志乱序** | 允许出现槽位空洞，可乱序确认 | 严格顺序追加，不允许空洞 |
| **选主条件** | 无严格限制（谁编号大谁赢，需事后补齐日志） | 严格限制（日志必须最新才能当选） |
| **实现难度** | 极高（每家公司实现都不太一样） | 较低（有极其明确的实现规范） |
| **代表应用** | Google Spanner, Chubby, 微信 PhxSQL | Etcd, Consul, TiKV, Redis Sentinel |

## 4. 结论

可以将 Raft 看作是 **Paxos 算法在工程实践上的一个“特化版本”**。
Raft 牺牲了一丁点理论上的并发度（如强制日志顺序、强 Leader），换取了整个算法极其清晰的逻辑和简单的实现路径。在目前的工程界，如果需要从头实现一个分布式共识系统，**Raft 几乎是唯一的首选**。而 Paxos 则更多地作为分布式理论的基石，或者在一些历史悠久、对极端并发有特殊要求的老牌顶级系统中固化存在。
