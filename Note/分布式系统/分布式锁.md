# 分布式锁 (Distributed Lock)

## 什么是分布式锁？
在单机多线程环境中，我们通常使用本地锁（如 C++ 的 `std::mutex` 或 Java 的 `synchronized`）来避免多个线程同时修改共享变量导致的数据不一致问题。当系统演变为分布式集群部署时，原本的基于本地内存的锁就无法跨越多个物理机或进程生效了。

**分布式锁**，是指在分布式系统环境下，为了控制多个不同的进程/节点对共享资源进行互斥访问而实现的一种锁机制。它可以保证在分布式系统中，同一个时刻只有一个客户端能够获取锁并执行相应的业务逻辑。

## 为什么需要分布式锁？
*   **避免数据冲突与不一致**：例如电商抢购时的库存扣减（避免超卖）、金融账户的金额变更等，多个微服务实例同时操作同一条数据时需要排队。
*   **避免重复执行**：例如多个节点部署了相同的定时任务，为了防止同一个任务在同一时刻被多个节点重复执行，通常需要使用锁。

## 分布式锁必须具备的特性
1.  **互斥性**：任何时刻只能有一个客户端持有某一把锁。
2.  **防死锁**：即使持有锁的客户端发生崩溃、宕机或网络分区，锁也能在设定的合理时间后被自动释放（通常采用 TTL 超时机制）。
3.  **高可用、高性能**：获取和释放锁必须非常高效，且锁服务本身需要具备容错性。
4.  **解铃还须系铃人（安全性）**：加锁和解锁必须是同一个客户端。不能把别人加的锁给错误释放掉。
5.  **可重入性（可选）**：同一个节点/线程在持有锁并未释放时，可以再次成功获取该锁，避免自我死锁。

## 常见的分布式锁实现方案

### 1. 基于 Redis 实现（极常用）
利用 Redis 的内存单线程高并发特性。
*   **加锁指令**：`SET key unique_value NX PX milliseconds`（NX 保证互斥，PX 保证超时自动释放）。
*   **解锁方式**：必须使用 **Lua 脚本**，先判断 value 是否是自己当初设置的 `unique_value`，如果是再执行 `DEL` 删除操作，保证解锁的原子性。
*   **高级特性 (如 Java 中的 Redisson 库)**：
    *   **看门狗 (WatchDog)**：开一个后台线程，业务没执行完时自动延长锁的过期时间，防止业务执行过慢导致锁提前释放。
    *   **Redlock (红锁)**：向多个独立的 Redis Master 节点同时申请锁，只有多数派（N/2 + 1）成功才算成功，解决 Redis 宕机主从切换导致的锁丢失问题。

### 2. 基于 ZooKeeper 实现
利用 ZK 的分布式协调强一致性。
*   **核心原理**：客户端尝试在特定的 ZNode 下创建**临时顺序节点（Ephemeral Sequential）**。
*   **加锁逻辑**：判断自己创建的节点序号是不是目录下所有节点中**最小的**。如果是最小的，则认为加锁成功。如果不是，则向排在自己前面的那个节点注册 Watcher 监听器并阻塞等待。
*   **优点**：
    *   具备天生的公平性（先创建节点的客户端先获得锁）。
    *   无需考虑超时续期问题（客户端断开连接，Session 失效，临时节点由 ZK 自动删除，天然防死锁）。
*   **缺点**：加锁解锁涉及 ZK 内部的增删写操作，性能不及纯内存的 Redis。

### 3. 基于 关系型数据库 (MySQL) 实现
*   **原理**：利用数据库表的 **唯一索引 (Unique Key)** 冲突，抢占插入一条记录；或者在事务中使用排他锁 `SELECT ... FOR UPDATE`。
*   **缺点**：性能最差，严重强依赖数据库单点，实现超时释放非常复杂，通常只适用于并发量极小的低频内部工具场景。
